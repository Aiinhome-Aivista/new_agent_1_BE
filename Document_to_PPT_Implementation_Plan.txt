IMPLEMENTATION PLAN
Document-to-Presentation Generator
Current Project Refactoring Plan

============================================================
1. OBJECTIVE
============================================================

Transform the current Proposal/RFP-focused presentation generator into a
generic Document-to-PPT Generator.

Target behavior:

User uploads any technical/project document
        |
        v
Document Understanding
        |
        v
Content Analysis
        |
        v
Dynamic Slide Planning
        |
        +-----------------------------+
        |                             |
        v                             v
Document-specific slides       Mandatory common slides
                                      |
                                      +-- Technology
                                      +-- Cost
                                      +-- Reference Architecture
                                      +-- Landscape Architecture
                                      +-- Thank You
        |
        v
Presentation IR
        |
        v
PPTX Renderer
        |
        v
Final PPT


CORE REQUIREMENT
----------------

The uploaded document determines the content and dynamic slides.

The following slides must always be present:

1. Technology Stack
2. Cost Estimation
3. Reference Architecture
4. Landscape Architecture
5. Thank You


============================================================
2. CURRENT PROJECT APPROACH
============================================================

The current project already contains reusable components such as:

- Document upload/extraction
- Intake/analysis agents
- Requirement analysis
- Design agent
- Orchestration
- LLM abstraction
- RAG/vector storage
- PPTX generation
- Reference architecture generation
- Landscape architecture generation
- Structured JSON IR
- Proposal workflow/API
- Pause/resume/cancel workflow support

Therefore, the project should NOT be rewritten from scratch.

The existing system should be refactored from:

    Proposal/RFP -> Proposal PPT

to:

    Any Document -> Document-specific PPT + Mandatory Common Slides

4. PHASE 1 - GENERIC DOCUMENT UNDERSTANDING
============================================================

Current problem:
The Intake Agent is heavily oriented toward RFP/proposal content.

Current classification includes concepts such as:
- Background
- Requirements
- Financial & Sizing
- Compliance & Security
- Other

New requirement:
The system must understand any technical/project document.

Create:

    agents/document_understanding_agent.py

Responsibilities:

1. Identify document type.

Possible types:

- RFP
- Technical Design
- High-Level Architecture
- Low-Level Design
- Solution Architecture
- Project Proposal
- Case Study
- Product Specification
- Requirements Specification
- Migration Architecture
- AI/ML Architecture
- Other Technical Document

2. Extract:
   - Document title
   - Domain
   - Summary
   - Main topics
   - Sections present
   - Architecture presence
   - Workflow presence
   - Security presence
   - Technology presence
   - Cost presence
   - Implementation plan presence
   - Cloud provider
   - Data/integration information

3. Do not invent information that is not present in the source.


Example output:

{
  "document_type": "Technical Architecture Specification",
  "title": "...",
  "domain": "AI / ITSM",
  "summary": "...",
  "sections_present": [
    "Executive Summary",
    "Architecture",
    "Technology",
    "Security"
  ],
  "has_architecture": true,
  "has_workflow": true,
  "has_security": true,
  "has_rag": true,
  "has_technology": true,
  "has_cost": false,
  "has_implementation_plan": false,
  "cloud_provider": "Not Specified"
}

    Document Specified
    Recommended
    Estimated


============================================================
13. PHASE 10 - COST SLIDE
============================================================

Cost slide is mandatory.

Two modes:

MODE A:
The document contains cost information.

Display:

    Document-Specified Cost

MODE B:
The document does not contain cost information.

Generate:

    Estimated Cost

based on:
- Technology
- Infrastructure
- Cloud
- Expected workload
- Architecture
- Deployment assumptions

Clearly label estimated values.

Do NOT invent a client budget.

Do NOT use fake values such as:
- $250,000
- Acme Corporation
- 14 weeks

unless they are actually present in the document.

Also remove Azure-specific assumptions from generic cost calculation.

Use:

    Cloud Provider: AWS / Azure / GCP / On-Prem / Not Specified

15. PHASE 12 - LANDSCAPE ARCHITECTURE
============================================================

Landscape Architecture is mandatory.

It represents the deployment/infrastructure view.

Cloud provider must be detected from the document.

Rules:

    AWS
      -> AWS landscape

    Azure
      -> Azure landscape

    GCP
      -> GCP landscape

    On-Prem
      -> On-Prem landscape

    Not specified
      -> Generic logical deployment landscape

Do NOT default to Azure when the document does not specify Azure.

30. IMPORTANT IMPLEMENTATION RULES
============================================================

RULE 1:
The uploaded document is the primary source of truth.

RULE 2:
Dynamic slides are determined by the document.

RULE 3:
These slides are always present:

    Technology
    Cost
    Reference Architecture
    Landscape Architecture
    Thank You

RULE 4:
Do not invent client names, budgets, timelines, technologies or
architecture components.

RULE 5:
If information is missing, explicitly say:

    "Not specified in source document"

RULE 6:
If a value is estimated, label it:

    "Estimated"

RULE 7:
Do not assume Azure, AWS or GCP unless supported by the document.

RULE 8:
LLM decides content; Python enforces presentation structure.

RULE 9:
Existing upload, workflow, download, pause/resume/cancel and RFP
functionality should be preserved during refactoring.

RULE 10:
The final PPT must be generated from a structured Presentation IR,
not directly from an unstructured LLM response.
